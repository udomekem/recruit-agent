# Phase 4 Design: Recruiter dashboard

Approved by Mani 2026-11-08 with all five checkpoint defaults (Q1 to Q5). Input: `stages/01-brief/output/phase-4-brief.md`
(approved 2026-11-08, five defaults, built locally and Vercel ready). Says WHAT and WHEN;
HOW belongs to stage 03.

---

## 1. Shape

```
browser ──cookie──▶ dashboard (Next.js, server side) ──bearer token──▶ API (FastAPI) ──▶ Postgres
```

- The browser talks only to the dashboard. Every API call is made on the dashboard's
  server (server components and server actions), which adds the recruiter token. The
  token and the API address are server only settings, never `NEXT_PUBLIC_`.
- The dashboard holds no business rules: ranking, bands, overrides and the agreement rate
  come from the API. It only shows them and sends decisions.
- New container `dashboard` in Docker Compose, port 3000. Settings from environment
  variables only, no local file writes, so phase 10 can deploy the same build to Vercel.

## 2. Sign in (brief Q1)

| Item | Value |
|------|-------|
| Account | one recruiter; password from `DASHBOARD_PASSWORD` in `.env` (generated by `make local-env`) |
| Session | signed, httpOnly, SameSite=Lax cookie (Secure over https), 8 hours; signing key `SESSION_SECRET` (generated) |
| Guard | every page and action except sign in requires a valid session; otherwise redirect to sign in |
| Brute force | 5 failed attempts per 15 minutes, then a wait |
| Forms | server actions only accept same origin requests (built into Next.js), so no cross site posting |
| Sign out | clears the cookie |

## 3. Pages

| Page | Shows | Actions |
|------|-------|---------|
| Sign in | password field | sign in |
| Jobs | each job: title, state, approved rubric version, counts by state, undecided count, agreement rate | open a job |
| Job | candidates ranked by score: rank, label ("Applicant 7"), total, band, flags, knockouts, state; filters for band, flag and state; agreement rate; a banner when scores are on an older rubric | review next undecided; rescore (when outdated) |
| Candidate | left: each criterion with verdict, reason, weight and quote; answers with rule outcome; reasons; flags (injection and hidden text first, in red); rubric, prompt and model versions. Right: the redacted CV text with each quote highlighted; clicking a criterion scrolls to its quote. Below: the audit timeline | shortlist, reject (with reason), previous, next |
| Review queue | NEEDS_REVIEW candidates with the last reason | retry, reject |

Contact details (brief Q2): a "Contact" panel appears on the candidate page only once the
candidate is shortlisted or later; before that, name, email and phone are never sent to
the browser.

## 4. Review flow and keys

| Key | Action |
|-----|--------|
| `j` / `k` | next / previous candidate (rank order, filters applied) |
| `s` | shortlist: opens the decision box |
| `r` | reject: opens the decision box |
| `Enter` | confirm the decision; the next undecided candidate opens |
| `Esc` | close the box |
| `?` | key help |

The decision box shows the recommendation. When the decision agrees (or the band is
maybe), the reason is pre-filled ("Agrees with the recommendation: advance") and `Enter`
confirms: two actions. When it is an override, the box says so, the reason field is
empty and required (at least 10 characters), and `Enter` confirms after typing. Keys do
nothing while typing in a field. A focused button is always visible (keyboard users) and
every action also has a button (mouse users).

## 5. API additions

| Endpoint or change | Who | Behaviour |
|--------------------|-----|-----------|
| `GET /jobs` | recruiter | jobs with state, rubric version, counts by candidate state, undecided count, agreement summary |
| `GET /jobs/{id}/candidates` (extended) | recruiter | adds `decision` (if any), `override`, and a job `agreement` summary: decided, agreed, overrides, rate |
| `POST /candidates/{id}/shortlist` and `/reject` (extended) | recruiter | records a Decision row in the same transaction as the move (section 6); an override with a reason under 10 characters is refused (422); `expected_version` required from the dashboard |
| `GET /candidates/{id}/contact` | recruiter | name, email, phone only when the state is SHORTLISTED or later and not erased; otherwise 403; every successful read writes an access event |
| `GET /review-queue` | recruiter | NEEDS_REVIEW candidates and jobs with the last reason |
| `POST /jobs/{id}/rescore` | recruiter | queues a rescore for every SCORED candidate whose latest score is on an older rubric version than the approved one; returns the count; writes a job audit event |
| Rescore worker job | system | runs the phase 3 scorer against the current approved rubric; stores a new Score row (unique per candidate and rubric, so a repeat is a no-op); no state change; failure keeps the old score and records the error on the job audit |

The existing `GET /candidates/{id}`, `/score` and `/parse` already return only the label,
never the name.

## 6. Entities

### Decision (one per recruiter decision on a scored candidate)
| Field | Type | Notes |
|-------|------|-------|
| id, candidate_id | UUID | |
| score_id | UUID, nullable | the score the recruiter saw; null for unscored (test) candidates |
| recommended | enum: advance, maybe, reject, none | the band at decision time |
| decision | enum: shortlist, reject | |
| override | bool | shortlist of reject, or reject of advance; never for maybe or none |
| reason | text | the audit reason as typed or pre-filled |
| actor_id, created_at | | |

Erasure clears the Decision reason (a recruiter may have typed personal details) and keeps
the rest for the agreement rate.

**Agreement rate** = decisions that are not overrides / all decisions with a
recommendation of advance or reject. Maybe and none are shown as counts, not in the rate.

### AccessEvent
| Field | Type | Notes |
|-------|------|-------|
| id, candidate_id, actor_id, what ("contact"), created_at | | Privacy Act: who saw contact details and when. Erasure keeps the row (no personal data in it) |

## 7. Side effects

| Effect | Idempotency | Failure |
|--------|-------------|---------|
| Decision | the move's expected version and idempotency key; Decision row in the same transaction | stale page: 409, the dashboard says "This candidate changed since you opened it" and reloads; no second decision |
| Rescore | unique Score per candidate and rubric; job is a no-op when the latest score is current | old score stays; error on the job audit |
| Contact read | read only, plus one access event | 403 before shortlist |

## 8. Failure modes and abuse cases

| Case | Expected behaviour |
|------|-------------------|
| Someone opens the dashboard without signing in | redirect to sign in; API never called |
| Token in the browser | never: server side calls only; e2e test checks every page, script and response |
| Password guessing | locked out for 15 minutes after 5 failures |
| Two tabs decide the same candidate | the second gets 409 and a message |
| Override with "ok" as the reason | refused by the form and by the API |
| CV text contains HTML or script | rendered as text, never as HTML; quotes highlighted by text match, not by inserting markup from the CV |
| Very long CV | scrolls; highlight still works |
| A quote appears twice in the CV | the first match is highlighted, the criterion lists both |
| API down | a clear error page; nothing is decided |
| Candidate erased while open | the page shows "erased"; decisions refused |
| Rubric revised after scoring | banner and a rescore button; decisions still allowed on the old score, which the Decision row records |

## 9. Tests and checks (maps every brief bar)

| Brief bar | How |
|-----------|-----|
| Review speed: at most 2 actions per decision | Playwright test on a seeded job of 50 candidates that agree with the recommendation: `s` or `r`, then `Enter`, 50 times; counts key presses and clicks; ends with 0 undecided. Overrides are a separate test (typing the reason is not counted as an action) |
| Agreement rate 100% | API test table of about 15 pairs (each band x each decision, none, maybe) checks `override` and the rate |
| Override reason 100% refused | API tests (no reason, "ok", 9 characters) and a form test |
| Blind review: 0 | Playwright reads the DOM and every response body of the job and candidate pages before shortlist: no seeded name, email or phone; after shortlist the contact panel shows them |
| Token exposure: 0 | Playwright collects every page's HTML, every script file and every response: the token string never appears |
| Accessibility: 0 serious or critical | axe on sign in, jobs, job, candidate, review queue |
| Speed: under 300 ms at the 95th percentile | API test: 200 seeded candidates with scores, 50 calls to the ranked list |
| Phase 3 bars still pass | rescore uses the same scorer; `make eval-score` once before closing |
| Vercel ready | `next build` in CI with only environment variables; a lint rule fails on `NEXT_PUBLIC_` secrets |

**Seed data (brief Q4)**:
- `make demo-seed`: creates the three phase 3 jobs through the API, replaces each draft
  rubric with the fixed phase 3 rubric, approves it, and applies the 45 scoring CVs
  through the apply page with their answers. Real pipeline, about $0.12.
- `make demo-seed-offline` (tests and CI): writes the same jobs and candidates straight to
  the database with stored redacted text and scores built from the coverage plans (quotes
  taken from the CV text). No model, no key.

End to end tests run against the Docker stack seeded offline.

## Checkpoint questions

| # | Question | Default if no answer |
|---|----------|---------------------|
| Q1 | Where the browser tests run | In the official Playwright Docker image, locally and in CI, so nothing is installed on Windows (about 2 GB of disk once) |
| Q2 | What counts as an action for the speed bar | Key presses and clicks; typing a reason does not count. Agreeing takes 2 (key, Enter); an override takes 2 plus the typed reason |

| Q4 | Rescore scope | Only candidates still at SCORED (undecided); decided candidates keep the score their decision was made on |
